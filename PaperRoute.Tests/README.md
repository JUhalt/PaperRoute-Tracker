# PaperRoute.Tests

The automated test suite for PaperRoute Tracker: MSTest 4 tests written in VB.NET, on .NET 10 for Windows. Most tests call the services and models directly. The UI tests build the real windows, and the real main window (`LibraryBoard` drives `Form1`), on a temporary library. At v0.9.2 the suite has 147 source files, 1,188 test methods and 363 data rows, which run as 1,451 results: 1,446 pass and 5 are skipped (the on-demand rows below).

This file is the audit record of #150, which #44 box 4 cites: what the suite proves, the safety coverage it keeps, and what the v0.9.2 pass merged. The pass covered the 147 files on master at fb24242.

## Running it

From the repository root:

```powershell
dotnet test PaperRoute.Tests/PaperRoute.Tests.vbproj --configuration Release
```

A full run takes 15 to 25 minutes on the maintainer's computer, and longer when the computer is busy. CI runs the whole suite for every pull request to master and every push to it (`.github/workflows/build.yml`). To run one class, add `--filter "FullyQualifiedName~BackupRestoreTests"`. `ResponsivenessBudgetTests` is timed and many UI tests move the keyboard focus, so on a busy computer, or with another test run on the same desktop, one of them can fail; run that class again alone before reading the failure as a regression.

Two tests depend on a variable:

- `WindowChromeTests.TheFileDialogsGetTheThemesTitleBarFromTheDialogHook` (category `OnDemand`, five rows) is skipped unless `PAPERROUTE_FILE_DIALOG_TESTS` is set, because a file dialog leaves Explorer's view state for its folder under HKCU. CI sets it on its disposable runners (#196), and `ManualCertification/Build-ReleaseCandidate.ps1` leaves the category out. Do not set it on your own computer.
- `CertificationFixtureTests.WritesTheFixtureForACertificationOnDemand` runs every time, into its own temporary folder. With `PAPERROUTE_CERTIFICATION_FIXTURE` naming a new or empty folder, it writes the standing certification fixture and its backup there for the release VM, as [ManualCertification/README.md](../ManualCertification/README.md#standing-certification-fixture) describes.

A new test follows two rules:

- **Forms only on `StaRunner`.** A test that makes a Form, or any other control, makes it inside `StaRunner.Run` (or `RunOnStaThread` in `TestSupport`), never on the test's own thread or a thread it starts. A theme test passes its color mode to `StaRunner.Run` instead of setting it. The runner fails a stuck test in bounded time, closes the windows it left and puts the color mode back (#134). `StaRunnerGuard` fails any test that made a form off the runner, because a color-mode test after it in the same process can hang (#185).
- **Storage only under `RootOverride`.** A test that can reach a default storage root (settings, error reports, Diagnostics, the main window) sets `StorageEnvironment.RootOverride` to a folder from `CreateTemporaryRoot()` in its `TestInitialize`, and in its `TestCleanup` sets it back to `Nothing` and calls `DeleteTemporaryRoot`. The override is shared by the whole process, so the class is marked `<DoNotParallelize>`. Library files go under a temporary root too. No test may read or write the researcher's own profile; the view catalog checks this for every view (`StorageEnvironment.DefaultRootUses` stays 0).

## Removed or merged in v0.9.2

Nothing was removed outright. Four groups of tests that differ only by data became one data-row test each, with one row per old test. Each old test built its input, made one call and made one assertion; its row builds the same input and makes the same call and the same assertion, so a row passes exactly when its old test did. No issue names any of the ten old tests.
