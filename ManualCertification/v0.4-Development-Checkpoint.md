## Checkpoint scope

- Make portable restore validate and rebase managed packet files while retaining
  readiness state and exact version/submission/round references.
- Preserve staged packet snapshots when interrupted deletion recovery finds a
  conflicting destination; keep cleanup failures from misreporting a committed save.
- Give each managed packet-file record its own copy even when its source already
  lives in another part of the managed library.
- Reject removal of packet-linked versions/submissions and reject invalid packet
  references before a repository save can copy, stage, or replace files.
- Exercise the actual readiness and packet dialogs with disposable, in-memory
  fixtures, including long text and minimum windows.
- Reserve separate list/detail space in the vault and readiness views. Use
  scrollable read-only details and horizontally scrollable long list entries;
  keep requirement instructions from consuming the notes editor.

## Packet integrity checkpoint — 2026-09-12

The vault now supports explicit SHA-256 recording and background file checks.
Opening the vault inspects file availability without hashing file contents.
Recorded fingerprints begin as Not checked. Check Files distinguishes Unchanged,
Changed, Missing, Unavailable, No fingerprint, and Metadata only. Results are
labeled as the last observation rather than continuous monitoring.

Checks never overwrite a saved fingerprint. Replace Fingerprint requires an
explicit confirmation, and new fingerprints remain on the vault working copy
until both the vault and Manuscript Details are saved. Cancel and closing during
background work discard pending changes. No source file is written by hashing.
Managed copies and portable restore retain the original comparison point even
when paths or filesystem timestamps change.

The final full suite passed **396 tests, zero failures or skips** (42 seconds).
This adds 18 service tests, seven integration cases, and one repeated-resize and

records share the same ID. Each working file record now has its own observation.

## Connected workflow checkpoint — 2026-09-12

navigation using the selected records' IDs. The vault labels its readiness,
version, or submission filter and provides Show all. New packets inherit visible
context defaults. Save & Go To commits the child dialog to the Manuscript Details
working copy before opening another dialog; the outer Save remains necessary.

An unlinked packet can open Record Journal Submission. Cancel returns to the
preparation packet without creating an event. Successful recording validates a
complete candidate before adopting the new submission, packet association, and
normal lifecycle changes. Incomplete readiness does not block it. The packet
retains its exact version without rewriting that version's earlier provenance.

## Migration, recovery, and theme checkpoint — 2026-09-12

Two schema writers no longer remove a previous schema backup before replacing
the schema file. Locked-schema tests cover versions 1–4, preserve every original
byte and prior backup on failure, and verify that an unlocked retry completes.

Checked-in synthetic Schema 4 JSON fixtures use the actual older record shape,
without readiness or packet fields. They include structured authors, journal
snapshots, revision history, recorded and unavailable audit dates, managed and
linked files, a missing external attachment, unresolved historical IDs, Published
and File Drawer records. Migration checks compare every source file byte,
preserve existing history, and prove repeat-run idempotency. Explicit save and
portable restore preserve the records and source files, rebasing managed paths
only. A future-schema case checks all current and legacy roots remain unchanged.
These fixtures represent v0.3 data shapes; they do not certify an installed upgrade.

Version recovery now preserves both staged and destination directories when the
destination already exists, including an empty destination. Packet recovery runs
independently if version recovery cannot finish. Six regressions cover both
conflict kinds, independent packet restoration, combined nonfatal warnings, and
a successful retry after resolving an empty conflict.

Light-theme action and link text is darker, and dark-theme destructive actions
use a slightly brighter red, so application-owned normal and hover text meets
the 4.5:1 contrast check on the tested surfaces. Four invisible-form smoke cases

save boundaries. They restore the test process's color mode and never change

## Release preparation — 2026-09-12

The project now declares product version `0.4.0` and assembly/file version
`0.4.0.0`. Candidate release notes, the user guide, README, roadmap, changelog,
and upgrade notes agree that v0.4 remains unreleased. The guide distinguishes
the partial Excel export from the complete portable ZIP backup. Published
payloads now include the repository's `LICENSE.txt` and `NOTICE.md`.

[`Build-V04ReleaseCandidate.ps1`](Build-V04ReleaseCandidate.ps1) builds and tests
an isolated output tree, packages the self-contained application, and verifies
versions, package/feed identity, payload bytes, legal notices, and SHA-256 hashes.
It records the exact source snapshot and rejects changes during the run. See
the [packaging and installer instructions](v0.4-Release-Packaging.md).

The disposable demo's `--primary` option places the real dialog on the primary
display and reports its actual DPI. A native Light vault run reported **120 DPI
at 125% scaling**: both lists, bounded scrollable details, and all actions were
visible at minimum size. Tab reached the packet details and New Packet action;
Enter opened the editor. The remaining readiness/theme/scaling and complete
keyboard cases have not been certified by this observation. Windows scaling
was not changed during this pass.

A separate powered-off linked clone of an existing clean Windows snapshot was
prepared for installation tests. Candidate inputs are read-only, evidence has a
dedicated writable share, and networking/clipboard/drag-and-drop are disabled.
The original VM and snapshot contents were not booted or restored. Guest login
and Guest Additions still need verification before any installation case runs.
The reusable helper requires explicit source VM and snapshot IDs; host-specific
IDs and its configuration evidence remain in ignored local test results.

The official v0.3.0 installer, full package, and portable ZIP were downloaded for
the upgrade fixture. Each matches both its published SHA-256 and GitHub asset
digest. The historical `releases.stable.json` matches GitHub's digest and correctly
describes the full package, but differs from the old published checksum list.
That list also includes local packaging files not uploaded to the release. The
v0.4 release workflow now stages a GitHub draft, compares uploaded package bytes
and feed metadata, adds the required documents and checksums, and downloads the
entire asset set again before publishing that verified release ID. Stable release
preflight rejects the current unreleased documentation markers. This sequence
has not been exercised as a live release. Original v0.3 assets and checksum files
have been retained unchanged.
