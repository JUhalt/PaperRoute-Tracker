# v0.4 candidate packaging and installer certification

`Build-V04ReleaseCandidate.ps1` prepares a local Windows x64 candidate. A successful
run produces `candidate-verification.json`; it does not certify installation,
publish a release, or change an installed PaperRoute application.

## Build a candidate

Use PowerShell 7.2 or newer on Windows with the .NET 10 SDK, Git, and `dnx` available. Finish
source edits before starting. The application project must explicitly declare
`Version` as `0.4.0` and both `AssemblyVersion` and `FileVersion` as `0.4.0.0`.
The exact release notes must exist at `docs/releases/0.4.0.md`. The script rejects
stale version declarations before building.

From the repository root:

```powershell
pwsh -NoProfile -File .\ManualCertification\Build-V04ReleaseCandidate.ps1 `
    -OutputDirectory .\artifacts\v0.4.0-candidate-01 -PreflightOnly

pwsh -NoProfile -File .\ManualCertification\Build-V04ReleaseCandidate.ps1 `
    -OutputDirectory .\artifacts\v0.4.0-candidate-01
```

The explicit output directory must be a fresh subdirectory of the repository's
Git-ignored `artifacts` directory. An existing empty directory is accepted;
nonempty directories and paths through junctions/symlinks are rejected. The script
never cleans up an older attempt. Select another directory after a failed run.
`-PreflightOnly` performs read-only checks and does not create output directories.

The script builds the Release solution, runs the entire test project, publishes a
self-contained `win-x64` payload, and uses pinned Velopack CLI **1.2.0** to package
it. Build intermediates use .NET's `--artifacts-path`, preserving the ordinary
Visual Studio output folders. The test project copies its checked-in schema
fixtures to its output directory, including when outputs are isolated this way.
NuGet and `dnx` may populate their normal dependency
caches. Velopack's application-hook check remains enabled; the application handles
that hook before normal storage initialization. The script never runs Setup,
Update, or a normal interactive PaperRoute launch. See the official
[.NET build options](https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-build)
and [Velopack packaging CLI](https://docs.velopack.io/reference/cli/content/vpk-windows).

The package identity remains `JUhalt.PaperRouteTracker`, with
`PaperRouteTracker.exe` as the entry point. Stable `0.4.0` uses the `stable`
channel. An explicit `-Version 0.4.0-rc.1` uses `preview` and requires matching
project `Version` and `docs/releases/0.4.0-rc.1.md`; numeric assembly/file versions
remain `0.4.0.0`. Velopack package versions use three numeric components, and
channel feeds are named `releases.<channel>.json`.
[Version guidance](https://docs.velopack.io/packaging/overview),
[channel guidance](https://docs.velopack.io/packaging/channels).

## Read the evidence

| Output | Purpose |
| --- | --- |
| `logs/` | Separate build, test, publish, and package command output |
| `tests/PaperRoute.Tests.trx` | Full automated result; every discovered test must pass |
| `publish/` | Verified self-contained application payload |
| `releases/` | Full update package, Setup, portable ZIP, and channel metadata |
| `releases/SHA256SUMS.txt` | SHA-256 and size-independent identity for every generated release asset |
| `candidate-verification.json` | Versions, source commit/status, test count, package/feed checks, hashes, and signature status |
| `source-files.json` | Hashes of tracked and non-ignored untracked source files at the start of the run |

Verification checks ProductVersion, FileVersion, and AssemblyVersion; required
runtime files; package ID/version in the NuGet manifest; matching application DLL
bytes in the full package and portable ZIP; and the full package's identity, size,
and SHA-256 in its channel feed. Both archives must also contain the unchanged
repository `LICENSE.txt` and `NOTICE.md`. It hashes every release asset and checks
those hashes again before writing successful evidence. Source hashes and HEAD
must remain unchanged through the run. These fields follow Velopack's
[asset model](https://docs.velopack.io/reference/cs/Velopack/VelopackAsset) and
[feed model](https://docs.velopack.io/reference/cs/Velopack/VelopackAssetFeed).

This mirrors the existing release workflow's package identity, title, author,
icon, runtime, and channel strategy. It deliberately starts with no prior release
download, so it produces a full-package candidate and does not certify delta
updates. The current workflow supplies no signing configuration; the evidence
records the actual Setup Authenticode status rather than claiming it is signed.
A dirty checkout is recorded and may be useful during development; final release
evidence must identify the committed source that is actually tagged.

The candidate checksums describe **local** packaging output. Velopack's GitHub
uploader selects files from `assets.<channel>.json` and regenerates the uploaded
feed from those package entries. A previous-version seed and internal metadata
can therefore appear in the local directory without becoming remote assets.
Final publication must verify downloaded draft assets and checksum their actual
bytes; do not reuse a local directory checksum manifest as proof of the published
asset set. This behavior is explicit in the pinned
[GitHub uploader](https://github.com/velopack/velopack/blob/1.2.0/src/vpk/Velopack.Deployment/GitHubRepository.cs)
and [build-asset list](https://github.com/velopack/velopack/blob/1.2.0/src/vpk/Velopack.Core/BuildAssets.cs).

The release verifier has a separate local regression harness:

```powershell
pwsh -NoProfile -File .\ManualCertification\Test-ReleaseAssetVerifier.ps1
```

It copies the current verifier into synthetic repositories and supplies a local
`gh` mock. Its fifteen cases exercise successful full/delta staging and final
verification, differing feed formatting and prior seeds, corrupted bytes and
metadata, inconsistent package types, missing assets/documents, invalid checksums,
and changing draft state. It performs no network calls, builds, or installer
launches. Reports and logs remain under ignored `artifacts/release-verifier-tests`;
these checks complement actual uploaded-asset and installed-app certification.

## Install and upgrade only inside a disposable Windows environment

A custom installation directory does **not** isolate the user's PaperRoute data,
Start Menu/Desktop shortcuts, or installed-app registry records. Use a disposable
Windows account or VM for real installer certification, with synthetic fixtures
or explicit copies of data. Preserve existing certification VMs and snapshots;
create a separate disposable clone for this run.

For the reviewed local VirtualBox installation,
[`New-V04CertificationVm.ps1`](New-V04CertificationVm.ps1) defaults to a read-only
plan for a separate linked clone of the exact clean snapshot. Supply a unique
`-VmName PaperRoute-v04-Cert-<suffix>`, the reviewed `-SourceVmId` and
`-CleanSnapshotId`, and the existing candidate folder through `-InputDirectory`;
its explicit `-Execute` mode creates/registers the clone without
starting it. Inputs are shared read-only, and guest evidence has its own writable
folder. Review that plan and preserve the original snapshot/base disk on which the
linked clone depends. VirtualBox registers the new differencing disk against that
snapshot; the helper verifies this expected change while checking that the other
persistent source settings remain unchanged. Guest login and Guest Additions
still require verification.

Velopack Setup supports `--installto`, `--silent`, and `--log`. Silent setup
suppresses first launch, allowing the installed files to be checked before the
application is opened. The default installation root is
`%LocalAppData%\JUhalt.PaperRouteTracker`; the `current` subdirectory contains the
active application, and `Update.exe` lives at the installation root.
[Setup CLI](https://docs.velopack.io/reference/cli/content/setup-windows),
[Windows installation layout](https://docs.velopack.io/packaging/operating-systems/windows).

The following examples are **guest-only commands**, after copying verified assets
into that disposable guest. Replace the example paths with actual fixture paths.
Use `Start-Process -Wait` because the Setup program is a Windows GUI executable;
check its exit code before inspecting or launching the application.

```powershell
$setupPath = 'C:\PaperRouteCertification\assets\JUhalt.PaperRouteTracker-stable-Setup.exe'
$installRoot = 'C:\PaperRouteCertification\installed'
$setupLog = 'C:\PaperRouteCertification\setup.log'
$setupProcess = Start-Process -FilePath $setupPath -ArgumentList @(
    '--silent', '--installto', ('"{0}"' -f $installRoot),
    '--log', ('"{0}"' -f $setupLog)
) -WindowStyle Hidden -Wait -PassThru
if ($setupProcess.ExitCode -ne 0) { throw "Setup failed: $($setupProcess.ExitCode)" }

[Diagnostics.FileVersionInfo]::GetVersionInfo(
    (Join-Path $installRoot 'current\PaperRouteTracker.dll')
) | Select-Object ProductVersion, FileVersion
```

For a **v0.3.0 to v0.4.0** upgrade, first install the verified v0.3.0 Setup in the
guest, launch it, create/save the certification records, record the storage roots
and fixture hashes, then close it. Apply the verified v0.4.0 **full** package using
the updater belonging to that guest installation:

```powershell
$fullPackage = 'C:\PaperRouteCertification\assets\JUhalt.PaperRouteTracker-0.4.0-stable-full.nupkg'
$updatePath = Join-Path $installRoot 'Update.exe'
$updateLog = 'C:\PaperRouteCertification\upgrade.log'
$updateProcess = Start-Process -FilePath $updatePath -ArgumentList @(
    '--silent', '--rootDir', ('"{0}"' -f $installRoot),
    '--log', ('"{0}"' -f $updateLog),
    'apply', '--package', ('"{0}"' -f $fullPackage), '--norestart'
) -WindowStyle Hidden -Wait -PassThru
if ($updateProcess.ExitCode -ne 0) { throw "Upgrade failed: $($updateProcess.ExitCode)" }
```

Those flags are supported by the
[Velopack 1.2.0 Windows updater CLI](https://docs.velopack.io/reference/cli/content/update-windows).
Discover the actual asset names from `candidate-verification.json`; do not infer
that an arbitrary file with a similar name is the verified package. Never point
these commands at the developer's installed application or original data roots.

After each install/update, launch the guest application interactively and capture
its About version, first launch behavior, fixture persistence, managed/linked
file behavior, and usable workflow at the supported scaling/window sizes. Record
clean install and upgrade as separate cases. The local `apply --package` command
certifies package application; it does not exercise the real GitHub update check,
release-note prompt, download, or stable/preview channel choice. Those require
separate installed-app certification against the intended published feed.

The [v0.3 closure checklist](v0.3-Release-Closure-Certification.md) is historical
evidence and a useful checklist reference; its old test counts do not certify
v0.4. Keep v0.4 test reports, installer logs, screenshots, fixture hashes, and
final published-asset checksums together before marking release closure complete.
