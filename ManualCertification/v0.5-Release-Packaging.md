# v0.5 candidate packaging and installer certification

`Build-V05ReleaseCandidate.ps1` prepares and verifies a local Windows x64
candidate. It does not install the application, publish a release, or certify an
upgrade. The requirements below are a checklist, not a record of completed tests.
Keep the v0.4 scripts and certification records as historical evidence.

## Prepare and build a candidate

Use PowerShell 7.2 or newer on Windows with the .NET 10 SDK, Git, and `dnx`
available. Finish source edits before starting. The application project must
explicitly declare all three versions:

| Candidate | Project `Version` | `AssemblyVersion` and `FileVersion` | Exact release notes | Channel |
| --- | --- | --- | --- | --- |
| Stable | `0.5.0` | `0.5.0.0` | `docs/releases/0.5.0.md` | `stable` |
| Release candidate | `0.5.0-rc.1` | `0.5.0.0` | `docs/releases/0.5.0-rc.1.md` | `preview` |

Release-candidate numbers must be positive integers. Pass `-Version` explicitly
for an RC, and use a matching project version and release-notes filename. The
helper intentionally rejects v0.4 declarations and missing notes before any
build. A passing preflight alone is not a verified candidate.

Run from the repository root:

```powershell
pwsh -NoProfile -File .\ManualCertification\Build-V05ReleaseCandidate.ps1 `
    -OutputDirectory .\artifacts\v0.5.0-candidate-01 -PreflightOnly

pwsh -NoProfile -File .\ManualCertification\Build-V05ReleaseCandidate.ps1 `
    -OutputDirectory .\artifacts\v0.5.0-candidate-01

# RC alternative, after setting the matching project version and notes:
pwsh -NoProfile -File .\ManualCertification\Build-V05ReleaseCandidate.ps1 `
    -Version 0.5.0-rc.1 `
    -OutputDirectory .\artifacts\v0.5.0-rc.1-candidate-01 -PreflightOnly
```

The output must be a fresh subdirectory of the repository's Git-ignored
`artifacts` directory. Existing empty directories are accepted; nonempty
directories and paths through junctions or symlinks are rejected. Failed attempts
retain their logs; choose another directory for a retry. `-PreflightOnly` performs
read-only checks and creates no output directory.

The helper builds the Release solution, runs the full test project, publishes a
self-contained `win-x64` payload, and packages it with pinned Velopack CLI
**1.2.0**. It requires every discovered test to pass, with none skipped. Build
intermediates use `--artifacts-path`, separate from ordinary Visual Studio
outputs. NuGet and `dnx` may populate their normal dependency caches. Velopack's
application-hook check stays enabled; that hook runs before normal storage
initialization. The helper never runs Setup, Update, or an interactive app launch.

The package identity stays `JUhalt.PaperRouteTracker`; the entry point stays
`PaperRouteTracker.exe`. Changing from an RC to stable changes the version, notes,
channel, and output directory, and requires a new verified candidate.

## Verify the candidate evidence

| Output | Required evidence |
| --- | --- |
| `logs/` | Build, test, publish, and package command results |
| `tests/PaperRoute.Tests.trx` | Full automated result with every discovered test passing |
| `publish/` | Self-contained application and runtime files |
| `releases/` | One full package, one Setup, one portable ZIP, and channel metadata |
| `releases/SHA256SUMS.txt` | SHA-256 identities for the generated release assets |
| `candidate-verification.json` | Versions, source commit, test count, binary/package/feed hashes, signature status, and limitations |
| `source-status.txt` and `source-files.json` | Working-tree status and source-file hashes used for the run |

The helper checks the published ProductVersion, FileVersion, and AssemblyVersion;
required runtime files; package identity/version; matching application DLL bytes
inside the full package and portable ZIP; and the package's identity, version,
size, and SHA-256 in the channel feed. Both archives must contain the unchanged
repository `LICENSE.txt` and `NOTICE.md`. Source files and HEAD must remain
unchanged during the complete run.

The helper starts without a previous-package seed and does not certify delta
updates. It records the actual Setup signature status. A dirty checkout can
produce development evidence, but final release evidence must identify the
committed source that is tagged. Historical v0.4 results and older v0.5 development
test counts do not certify a later candidate.

Local candidate checksums identify local bytes. Final publication must separately
verify the actual uploaded asset set, download those assets, and confirm their
bytes and feed metadata. Packaging success does not certify the live updater's
channel selection, release-notes prompt, download, or restart behavior.

## Certify clean installation and the v0.4 to v0.5 upgrade

Perform installation only in a disposable Windows account or VM with synthetic
fixtures or explicit copies of data. A custom install directory does not isolate
PaperRoute's data, shortcuts, or installed-app registration. Preserve existing
certification VMs and snapshots; use a separate disposable environment for v0.5.
Do not point the commands below at a developer's installed app or original data.

`New-V05CertificationVm.ps1` derives from the v0.4 helper and defaults to a
read-only plan. After preparing an ordinary input folder beneath `artifacts`,
review the plan for the exact existing clean snapshot:

```powershell
pwsh -NoProfile -File .\ManualCertification\New-V05CertificationVm.ps1 `
    -SourceVmId 5fa6e065-d022-433a-a3f6-bea13c878dfd `
    -CleanSnapshotId 8ac98276-5de8-41f0-aef3-3d522231ab64 `
    -VmName PaperRoute-v05-Cert-candidate-01 `
    -InputDirectory (Join-Path $PWD 'artifacts\v0.5-certification-inputs')
```

Use a unique VM name for each attempt. The explicit `-Execute` option creates and
registers a linked clone without starting it; no clone is created by the example
above. The helper verifies the exact clean snapshot and requires the source VM to
be powered off. It preserves the original persistent configuration apart from
the required linked-disk registration and transient guest-status changes. Keep
the original snapshot and base disk because the clone depends on them. Inputs
are shared read-only, evidence has a separate writable folder, and networking,
clipboard, and drag-and-drop are disabled by default. Verify guest login and
Guest Additions after boot. Enable networking only for the separate live-feed
check when needed; local package application does not require it.

Record clean installation and upgrade as separate cases. Discover actual asset
names and hashes from `candidate-verification.json` rather than assuming a
similarly named file is the verified package. Record the guest, installation
root, candidate source commit, and asset SHA-256 values before starting.

For a clean installation, copy the verified Setup into the guest, then run these
**guest-only commands** with paths adjusted to that guest:

```powershell
$setupPath = 'C:\PaperRouteCertification\assets\JUhalt.PaperRouteTracker-stable-Setup.exe'
$installRoot = 'C:\PaperRouteCertification\installed'
$setupLog = 'C:\PaperRouteCertification\setup.log'
$setupProcess = Start-Process -FilePath $setupPath -ArgumentList @(
    '--silent', '--installto', ('"{0}"' -f $installRoot),
    '--log', ('"{0}"' -f $setupLog)
) -WindowStyle Hidden -Wait -PassThru
if ($setupProcess.ExitCode -ne 0) { throw "Setup failed: $($setupProcess.ExitCode)" }

[Diagnostics.FileVersionInfo]::GetVersionInfo(
    (Join-Path $installRoot 'current\PaperRouteTracker.dll')
) | Select-Object ProductVersion, FileVersion
```

Silent Setup suppresses first launch. Confirm the installed version and DLL hash
match the candidate before opening the app interactively. An RC uses its verified
preview assets and expected RC ProductVersion.

For **v0.4.0 to v0.5.0** upgrade certification:

1. Install the verified v0.4.0 Setup in the disposable guest. Launch it and save a
   synthetic library containing submissions, decisions, correspondence, versions,
   readiness profiles, submission packets, and reusable journal metadata. Include
   both managed files and linked external files.
2. Record the actual storage roots, Schema 5 marker, record identifiers, file
   hashes, and a portable backup made by v0.4. Close the old app before upgrading.
3. Apply the verified v0.5 full package with the updater from that guest
   installation. For stable, an example command is:

```powershell
$fullPackage = 'C:\PaperRouteCertification\assets\JUhalt.PaperRouteTracker-0.5.0-stable-full.nupkg'
$updatePath = Join-Path $installRoot 'Update.exe'
$updateLog = 'C:\PaperRouteCertification\upgrade.log'
$updateProcess = Start-Process -FilePath $updatePath -ArgumentList @(
    '--silent', '--rootDir', ('"{0}"' -f $installRoot),
    '--log', ('"{0}"' -f $updateLog),
    'apply', '--package', ('"{0}"' -f $fullPackage), '--norestart'
) -WindowStyle Hidden -Wait -PassThru
if ($updateProcess.ExitCode -ne 0) { throw "Upgrade failed: $($updateProcess.ExitCode)" }
```

4. Before first app launch, verify the installed DLL version and hash. Launch
   v0.5, capture About, and verify Schema 5 advances to Schema 6 with a preserved
   `schema.v5.bak`. Migration must preserve the existing manuscript/author JSON
   bytes and managed/linked files; capture these hashes before subsequent saves.
   Existing submissions should start with an empty response matrix.
5. Add reviewer comments linked to explicit decisions and revision rounds. Cover
   multiple reviewers, all four statuses, ordering, action/response/location/notes,
   and an edited Markdown export. Verify item Cancel and matrix Cancel discard
   edits; matrix Save alone changes only the outer working copy. Save Manuscript
   Details, restart the installed app, and confirm responses and their links persist.
6. Verify submission metadata edits retain the matrix, linked decisions cannot be
   deleted until responses are reassigned or removed, and export edits do not
   mutate stored responses. Create and restore a v0.5 portable backup in disposable
   storage, confirming response order, rounds, text, and existing file behavior.
7. Check the installed board and response dialogs at native 100%, 125%, and 150%
   scaling, minimum size, and maximized/restored size. Capture actual DPI evidence,
   readable long text, keyboard access, vertical shelf scrolling without phantom
   horizontal overflow, and reachable last-card actions. Development harness
   screenshots are useful context but do not certify the installed candidate.

Schema 6 prevents older applications from opening the normal newer library.
Do not restore a v0.5 backup into v0.4: the older restore format does not provide
that protection and cannot preserve reviewer responses. Use the retained
pre-upgrade backup when returning to v0.4. Test downgrade rejection only against
a disposable copy, preserving the original fixture and backup.

The local `apply --package` case certifies package application only. Separately
exercise the installed updater against the intended published feed and record
channel selection, version offered, release notes, download, restart, and
post-update data. An RC cannot stand in for final stable-feed certification.

Keep candidate logs, installed-app versions and hashes, migration snapshots,
fixture/backup comparisons, DPI screenshots, and final downloaded-asset evidence
together. Mark clean install, upgrade, portable restore, native UI checks, and
live updater checks complete only when their actual results are recorded.
