# v1.0.1 certification checklist

One ordered list of the checks for v1.0.1's certification ([#352](https://github.com/JUhalt/PaperRoute-Tracker/issues/352)). It follows the [standing procedure](Release-Certification.md) and the form of [1.0's checklist](v1.0-Certification-Checklist.md), cut to what a patch release changes. v1.0.1 is a patch on the same Windows Forms app: no new window, the Schema 9 library kept. So each check here comes from what changed since v1.0.0, and the lines 1.0.1 does not touch carry over from 1.0's certification (#313), each with its reason (**What carries over from #313**).

**How to use it.** Work down the list in order: A, B and C on the host; D, the candidate's publication; V, the VM on the published candidate; then the Stable lines, T and S; then F.
- **What the candidate's tag waits for.** D1 waits for A, B1, B2, an adversarial review of the candidate with nothing that must be fixed, and the maintainer's approval, which decision 9 gives on those conditions. B3 and the C lines run on the release commit too, and three of them need the maintainer at the PC (C1, C3's Narrator pass, C4), so they may follow D1. All of them run before T. A failure in C2, C3 or C4 after D1 is handled as a failure in V: a fix and a new rc.
- **The release commit.** The candidate is prepared twice. The first prep, PR #364, merged as 0db8bd0 with #358 and #361 named as known limits; after the maintainer's decision of November 14 at about 17:22 (decision 8), 0db8bd0 is not tagged, and its records on #352 stand as records of that commit. The second prep, on `release/v1.0.1-rc.1-b`, follows PR #366 (#361) and PR #367 (#358) and keeps the name `v1.0.1-rc.1`. A1, A3 and A4 run on its branch. Once they pass, its pull request merges (CI green, CLEAN). `<rc>`, the release commit, is that merge commit on master, as v1.0.0-rc.4 (36a8aad) and v1.0.0 (cc40d4b) were; A2, A5, B, C and D run on it, and D1 tags it. _PENDING
- The letters keep these lines apart from 1.0's. A line of 1.0's checklist is always written "1.0's E2.10" or "#313's E2.10".
- Each line names where it comes from and what a pass looks like. Replace its `Result: not run` with what happened: pass or fail, the numbers, the evidence file names.
- A line that carries over gives, in its Result, the 1.0 line it carries and that line's date.
- Post results to #352 as they come. Host evidence goes in `TestResults\v101-certification-evidence`, guest evidence on the VM's evidence share, and none under `%TEMP%`. Evidence JSON is preferred to screenshots (step 10).

**The rc, then Stable** (#352's decisions). As for 1.0:
- **The rc,** `v1.0.1-rc.1`: `Version` 1.0.1-rc.1, `AssemblyVersion` and `FileVersion` 1.0.1.0, and notes in `docs/releases/1.0.1-rc.1.md`. The version lines came with the first prep (0db8bd0), which was never tagged; the second prep rewrites the notes and documents for six fixes and changes no version line, so there is one public candidate and its notes say what it holds. release.yml publishes a tag with a hyphen as a prerelease on the Preview channel, not as Latest, and runs its Unreleased gate only for Stable.
- **Why an rc.** #339's change is on the path Velopack downloads through (`GatedDownloader` uses `OnlineAccess.CreateClient`). Only a published build shows a 1.0.1 install taking an update (S4).
- **Stable from the same code.** release.yml requires the vbproj's `Version` to equal the tag's, so the Stable prep (T2) changes the `Version` line and the release documents, and nothing else.
- **A failure after publication** is recorded on #352 at once. A failure in V means a fix and a new rc, certified as rc.1 was, with the lines its diff touches run again, as 1.0's rc.4 followed rc.3. After the Stable tag, the maintainer decides what follows.
