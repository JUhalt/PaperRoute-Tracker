# What headless cannot show

The checks in this project run on Avalonia's headless platform: windows live in memory, with Skia drawing real pixels, and no screen, no system and no person. This note lists what that leaves out, one row per limit: what the limit bounds, and what proves the limit holds or says where the real check is made. The plan's three limits (`docs/design/Avalonia-Migration-Plan.md:180` and the acceptance line of build issue 3) are rows 1 to 3.

Each row lands with the pull request that adds its proof, so no row names a test that does not exist yet. The numbers are the design's (harness and style design, part 2.7); the rows it gives to later pull requests are added by them: row 8 came with S6, and rows 6 and 7 are still to come.

`TheLimitsNoteNamesEveryLimitAndEveryRuleLinksIt` (`HeadlessLimitTests.cs`) keeps this note honest: it fails if the plan's three limits are missing here in its words, if a "Proved by" cell neither names a test in a code span nor starts with "A statement", if a test named in that column is not a test method of this project that CI runs (one marked `[Ignore]` or in the `Manual` category does not count), or if a rule's code file (every `.cs` file under `Legibility/` and `Parity/`, and `AccessibilityTreeTests.cs`) lacks the line `// Limits of headless: HeadlessLimits.md`.

| # | Limit | Bounds | Proved by |
|---|---|---|---|
| 1 | No UI Automation or AT-SPI tree. The tree tests walk Avalonia's own automation peers, not what a screen reader receives through UI Automation (Windows) or AT-SPI (Linux). Narrator and Orca stay the manual check 5 (plan :178, :180). | the tree tests (`AccessibilityTreeTests.cs`) | A statement: the headless platform has no accessibility backend. The keyboard test that asserts focus events Windows raises for UI Automation (`KeyboardAccessTests.vb`) stays a manual check. |
| 2 | Render scale 1 unless set. Headless draws one pixel per unit unless a test sets another scale; DPI scaling stays in the installed-app gates. | the pixel rules (R5's and R7's sweeps, `R5_NoLightPatchesOnTheDarkBoard`, P-R7 and the rules that follow them) | `HeadlessRendersAtScaleOneUnlessSet` |
| 3 | No native dialogs. No file dialog, browser launch or second window of the system opens; the tests drive stand-ins for every outcome (`PlatformCheckTests.cs`). | the platform tests | A statement: the real dialog and launcher are run by a person. The Linux window job under Xvfb runs the real platform check (`--platform-check`). |
| 4 | Light, no contrast and no change events. The headless platform reports a Light system with no contrast preference and never raises a colour change, so Windows' system colours (`GetSysColor`) are never read and `ColorValuesChanged` never runs. Each test drives a contrast theme itself, through `AppTheme.Follow` with a `ContrastPreference` of its own. | R2, R9 and the theme tests | `HeadlessReportsLightAndNoContrast` |
| 5 | No physical pointer. Pointer input is simulated (`Window.MouseMove`, `MouseDown`, `MouseUp`); the style gallery shows hover and press by setting the `:pointerover` and `:pressed` pseudo-classes. A button sets `:pressed` from its `IsPressed` when its template is applied, which clears it here, so the gallery's pressed specimens set it again each time their template has been applied (until #463 they were drawn hovered). They also take their face's transition away: a transition runs on the real clock here as well, a forced frame does not move it, and a face still easing shows a shade in between in a picture taken sooner than its 100 ms. A real mouse, pen or touch is checked by hand. | the style gallery | `EveryPressedSpecimenDrawsItsPressedBrush` and `EveryHoveredFocusedAndOffSpecimenDrawsItsStatesBrush` (`Styles/GalleryStateTests.cs`): each state specimen carries its pseudo-class and holds its state's brush when drawn, in all six theme cases. `NoStateSpecimenIsStillEasingWhenItIsShown`: each holds it at once, before any frame is drawn. |
| 8 | No system text size reaches headless. The headless platform has no text-size setting, and Avalonia 12.1.6 offers none to follow: no public type or member named like `TextScale`, `FontScale` or `TextSizeFactor` in any Avalonia assembly the app loads, the Windows, X11 and macOS back ends included, nor in Avalonia.Headless, the platform these tests run on, which is scanned as well. So no test here shows text following the system's text size. What is checked so far: that absence (`AvaloniaOffersNoTextSizeSetting`, which fails when an upgrade adds such a member), and the four fields the platform check (`--platform-check`) records for the real check: the system's text setting (Windows' `TextScaleFactor`; GNOME's `text-scaling-factor` and `Xft.dpi`), the window's render scaling, and the heights in the window's device pixels of a 13 px body line in Inter and of a fixed box 100 layout units high, which grows only when everything grows (`ThePlatformCheckRecordsTextScaleScalingAndLineHeight`). The Linux window job under Xvfb runs the check at the default and again with `Xft.dpi: 144`, and judges neither. The guest runs are still to come: the published trial's platform check in the Windows guest at Text size 100 % and 150 % and in the Ubuntu guest at text scaling 1.0 and 1.5, each with today's WinForms app beside it. Only they can say which happened (text grows: the line grows and the box stays; everything grows: both grow with the render scaling; or nothing changes), and this row then says it. Until then nothing about following the system text size is claimed. | the text-size statement (the plan's section 9) | `AvaloniaOffersNoTextSizeSetting` |
| 9 | Headless timings are not the window's. A headless run has no compositor, no screen refresh and no system input queue. | the budget tests | A statement: the window's own figures come from the measure mode (`--measure`) in a real window: the Xvfb job, and by hand on a desktop. |
